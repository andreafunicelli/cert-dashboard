# Cert Dashboard — Plan 3: Discovery and Deployment with Ansible Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Discover every TLS binding on the inventory's nginx and Apache servers through read-only Ansible runs and reconcile it into `server`/`binding`/`endpoint` rows without duplicates; deploy issued certificates host-atomically with canary-first batched rollouts, drift protection, config tests, on-target verification and automatic per-host rollback; give operators the Deploy screens, discovery actions and "Test pull"; and close v1 with the §10.4 acceptance run against SSH-enabled container targets.

**Architecture:** The worker registers `discover/default`, `discover/test_pull` and `deploy/default` through Plan 1's `JobRegistry`, plus the nightly `discovery` schedule, the deploy timeout callback and a deploy sweep tick step. `app/ansible/runner.py` wraps `ansible-runner` with an explicit environment, file-path-only secrets and an event parser; the two committed playbooks (`discover.yml`, `deploy.yml`) do the on-target work, while the nginx/Apache parsers, reconciliation, rollout planning and all bookkeeping run in Python on the worker. The queue gains typed control outcomes (pause, requeue, cancel) so a canary-paused deploy holds no claim, no slot and no lock. `web` only reads the database, computes previews and enqueues; it never runs Ansible, git or SSH.

**Tech Stack:** Plans 1–2 unchanged. `ansible-core` and `ansible-runner` are already locked runtime dependencies (Plan 1 Task 1) and `git`, `openssh-client` and `openssl` are already in the image; Plan 3 adds **no** runtime or dev dependency. Test-only: SSH-enabled target images built from a digest-pinned `debian:bookworm-slim` with Debian's `nginx`/`apache2`, `openssh-server`, `sudo`, `python3`, `openssl`, `git` and `procps` packages, built by a CI setup step and started by the tests with `--no-build --pull never`. These are implementation decisions, not quotations from the spec.

Plan 1 (`docs/superpowers/plans/2026-10-19-cert-dashboard-plan-1-core.md`) and Plan 2 (`docs/superpowers/plans/2026-10-25-cert-dashboard-plan-2-tls-scan-and-alerts.md`) Global Constraints, Contract decisions and Extension points remain binding.

## Global Constraints

- Plans 1–2 Global Constraints apply unchanged. **No new migration, table, column, enum value, index or seeded `app_setting` row.** Every setting used here already exists in the allowlist of `app/services/settings.py`: `inventory.repo_url`, `inventory.ref`, `inventory.path`, `inventory.webserver_var`, `discovery.nightly_at`, `discovery.enabled`, `deploy.batch_percent`, `deploy.concurrency`, `deploy.pause_after_canary`, `deploy.pause_timeout_hours`, `deploy.backup_retention_days`, `deploy.host_timeout_seconds`, `scan.timeout_seconds`, `ui.timezone`. No change to `app/crypto/*`, `store_key`/`unwrap_key`, PFX/export, or to Plan 2's scan, alert and digest contracts beyond the additive hooks named in the Contract decisions.
- Inventory (§6.1, §7.7, §3.6, §9.7): the static Git repository is the only source of servers; the worker keeps a read-only checkout under `/srv/inventory`, pulls with fetch-into-a-temp-ref then `git reset --hard` on a clean checkout before every discover and deploy job (and therefore before the nightly discovery), records `rev`/`rev_date`, keeps the last good revision when a pull fails and fails the job only when that checkout is older than 24 hours. The pull holds the `inventory:pull` lock and is a no-op if a pull completed less than 60 seconds ago. The dashboard never pushes. `inventory.webserver_var` (default `webserver_type`) with values `nginx`/`apache` names the webserver; otherwise discovery auto-detects it.
- `discover.yml` (§6.2): whole inventory by default, per group or host on demand; `nginx -T` (stdout+stderr) or `apachectl -S` (= `-t -D DUMP_VHOSTS -D DUMP_RUN_CFG`) + the concatenation, with file markers, of every file `-S` references **unioned with a recursive read of the `Include`/`IncludeOptional` paths of the main config** (the only source of files that hold global-level directives, and the sole source when `-S` yields no file list; Contract decision 8); `stat` and `openssl x509 -noout -fingerprint -sha256` for each certificate path; the key's public-key hash under `no_log: true`, `key_unreadable: true` for passphrase-protected keys; one §6.2 JSON document per host; parsers in `app/ansible/parse_nginx.py` / `parse_apache.py`; **read-only**: never writes files, never reloads, `become` only to read root-owned files.
- Reconciliation (§6.3, §9.5): one transaction per server; the §6.3 table row by row; unknown certificates are never imported; bindings and servers are never deleted; a host that previously had bindings and now yields zero is `parse_suspected` and its bindings are not deactivated; a binding appearing for the first time gets a derived endpoint.
- `deploy.yml` (§6.4): once per host; extra-vars carry file **paths** and a JSON `targets` array only; steps preflight (drift, free space ≥ 2× written size + 10 MB, baseline config test, leaf/key hash match), backup to `/var/backups/cert-dashboard/<job_id>/<absolute path>` (root `0700`, key backups `0600`, certificate backups ≤ `0644`, `manifest.json`, refuse to proceed if a backup is missing), atomic writes (key `0600`, certificate `0644` unless the old file was stricter, mode set before content), `restorecon` when SELinux is present, config test, reload, on-target verify (3 attempts, 2 s apart), automatic rollback on any failure from the first write through verification (steps 3–7, a fail-safe superset of §6.4 step 8's steps 5–7; Contract decision 17) with one rollback attempt only, idempotent re-runs, prune backups older than `deploy.backup_retention_days` (`0` = keep forever) keeping the newest backup of each path. Only certificate, chain and key files are ever written; every key-touching task is `no_log: true`; `become: true`.
- Rollout (§6.5, §3.6): revalidate trust at current UTC before planning and again at execution; targets = active bindings of the replaced certificate (`renews_id`) or the operator's explicit selection, excluding `key_mismatch`/`missing_file`, `unknown` only by audited override; one server per group of bindings; canary = operator pick or the first server of the smallest affected group; round-robin across groups then hostname; batch size `max(1, ceil(total_servers * batch_percent / 100))`, batch 0 = canary; pause after a successful canary (default on) releases the claim; Continue requeues at batch 1 and re-runs drift checks; paused jobs auto-cancel after `deploy.pause_timeout_hours`; the first failed host stops the rollout, in-flight hosts finish, remaining rows `skipped` (`rollout_stopped`); hosts per batch run with `deploy.concurrency` threads, **submitted incrementally** (never more than `deploy.concurrency` submitted-and-unfinished, nothing submitted after a failed result; Contract decision 14); a host locked by `deploy:<hostname>` is `skipped`, not failed; one deploy at a time under `deploy:global`; no job-level rollback.
- Preview (§6.6) is computed from the database and is advisory; the host re-checks drift.
- Timeouts and failures (§6.7, §7.2): per-host run `deploy.host_timeout_seconds` (default 600), per-task 60 s for commands that can hang; discover job 1800 s; deploy job timeout = distinct remaining hosts × host timeout + 900 s, cleared on pause and recomputed on claim; `ANSIBLE_HOST_KEY_CHECKING=True`, `ANSIBLE_NOCOLOR=True`, events consumed directly; unreachable = `transient_network`, retried for discovery only (3 attempts, 30/120 s, the 300 s step is unreachable under the cap); SSH authentication failure = `auth`, never retried, with a `known_hosts`/deploy-key hint; deploy max 1 attempt, never retried automatically (a retry is a new job with a new audit entry).
- Trust (§5.8): deploy requires `chain_status=trusted` at current UTC or an explicit admin-supplied reason recorded as a `deploy.chain_override` audit (certificate, previous status, actor, job, reason). The override **never** bypasses key presence/match, leaf validity, binding state, drift or config-test guardrails.
- Renewal (§4.6): `issued → deployed` only through `mark_deployed(db, renewal_id, job_id, actor, now)` after a **succeeded** deploy job with at least one succeeded binding row carrying the new fingerprint.
- Secrets (§3.4, §5.2, §6.1, §6.4, §9.1.4): no secret in argv, extra-vars, environment files, `ansible-runner` artifacts, job payloads/results/errors, audit rows, logs or UI. The SSH key and the TLS private key reach Ansible as `0600` files on the worker's tmpfs `/run/cert-keys`, deleted in `finally`; the vault password and Git token only as environment variables of the child process; every stored text passes `redact()` and is truncated.
- `web` enqueues only (§3.1): no Ansible, git, SSH or worker secret in the web process.
- Priorities (§3.2): deploy 300, on-demand discovery 200, scheduled discovery 100. Discovery shares the two-slot cap with scans; discovery and deploy are claimable only by a worker that has `ansible_ssh_key` (Plan 1 `_SSH_TYPES`).
- Lists and forms (§8, §3.7): server-side pagination, whitelisted sorts, bookmarkable filters, allowlisted JSON export, constant query count, CSRF on every POST, POST→303, htmx 422 fragments, usable without JavaScript, every mutation and its audit in one transaction.
- Tests (§10): Testcontainers `postgres:16` exactly as Plans 1–2; real `sshd` + nginx/Apache targets from `docker-compose.test.yml` profile `ssh-targets` (Contract decision 25); no test reaches the Internet; the Git inventory is a local bare repository created by the fixture. Integration tests need Docker and run only in GitHub CI; locally run `uv run ruff check .` and `uv run pytest -q tests/unit` (Docker-dependent topology cases skip). Coverage gates: 85% on `app/crypto`, `app/services/renewals.py`, `app/services/deploy.py` and `app/ansible/parse_*` (§10.3), 70% overall.

## Review Focus

- A canary-paused deploy holds no claim, slot, advisory lock or `timeout_at`, is never reaped, and resumes at batch 1 only through an audited Continue; a forgotten pause auto-cancels with `deploy.pause_expired` (Tasks 1, 17).
- No secret ever reaches argv, extra-vars, `ansible-runner` artifacts, logs, job rows or audit rows: canary vault passwords, Git tokens and key bytes are searched for in every artifact file (Tasks 2, 4, 14, 20).
- Discovery is read-only on the target, never duplicates `server`/`binding`/`endpoint` rows on re-runs, never deactivates bindings on a zero-binding dump of a previously populated host, and audits every binding transition through `audit_binding_state` (Tasks 8–10). Apache discovery also reads the recursively `Include`d files that `apachectl -S` does not list, so a globally included TLS configuration is found (Tasks 7–8).
- No task ever ships a live-file write path without its automatic rollback: Task 14 writes nothing but the backup tree, and the write, label, config-test, reload and verify steps arrive in Task 15 inside the one `block` whose `rescue` is the rollback (enforced by a static test).
- A deploy never writes a file twice on a host, never touches a binding in `key_mismatch`/`missing_file`, refuses to write over drifted files, rolls back every written file byte-for-byte on a failed write, config test, reload or verification, and marks a failed rollback as needing manual attention (Tasks 14–15).
- The first failed host stops the rollout: hosts of a batch are submitted incrementally up to `deploy.concurrency`, nothing is submitted after a failed result, in-flight hosts finish and unstarted rows stay unrun and become `skipped` (Tasks 12, 16); locked hosts are skipped without stopping it; deploy jobs never retry; `mark_deployed` runs only after a succeeded job with real succeeded binding evidence (Tasks 16–17).
- The trust override is reasoned, audited, bound to the status it overrode, and never bypasses key, leaf-validity, drift or config-test checks (Tasks 13, 16).
- The test harness really connects over SSH with pinned host keys and asserts filesystem and served-certificate state on the targets (Tasks 3, 8, 14–16, 20).

## Contract decisions and test conventions

These resolve points the spec leaves open. Each is the smallest choice consistent with §6; the reviewer validates them against the cited sections.

1. **Module layout (§3.5).** `app/ansible/runner.py` (ansible-runner wrapper and event parsing), `app/ansible/staging.py` (tmpfs secret files), `app/ansible/vault_client.py` and `app/ansible/git_askpass.py` (executable helpers that print a secret from their own environment), `app/ansible/parse_nginx.py`, `app/ansible/parse_apache.py`, `app/ansible/discovery.py` (playbook phases → §6.2 documents), `app/ansible/deploy.py` (per-host material staging, playbook invocation and outcome parsing), `app/ansible/playbooks/{discover.yml,deploy.yml,tasks/*.yml,files/prune_backups.py}`; `app/jobs/locks.py`; `app/services/inventory.py`, `app/services/discovery.py` (reconciliation), `app/services/deploy.py` (rollout and file-write planning, preview, start and operator controls — the §10.3 coverage-gated module; pure planning code here is shared by `web` and the worker and imports nothing from `app/ansible`), `app/services/deploy_runtime.py` (worker-side revalidation, host-result bookkeeping, sweep, timeout), `app/services/deploy_views.py` (read models); handlers `app/jobs/handlers/{ansible_context.py,test_pull.py,discover.py,deploy.py}`; web `app/web/deploy.py` plus routes added to Plan 2's `app/web/servers.py` and Plan 1's `app/web/settings.py`.
2. **Pausable, requeueable and cancellable claims (§6.5, §7.2, §3.6).** Plan 1's handlers can only succeed or fail, and `claim()` requires `attempt < max_attempts` while deploy jobs have `max_attempts = 1`, so a resumed canary job could never be claimed again. `app/jobs/queue.py` therefore adds typed control outcomes a handler raises — `JobPaused(resume_from_batch, result)`, `JobRequeued(run_after)`, `JobCancelled(message, result)` (all subclasses of `JobControl`) — that `JobRegistry.dispatch` passes through and `Worker._execute` maps, behind the same ownership fence as `_finish`, to `release_claim(..., to='paused'|'queued')` or `finish(..., 'cancelled')`. `release_claim` clears `locked_by/locked_at/timeout_at`, sets `paused_at` (pause) or `run_after` (requeue), stores `resume_from_batch`/`result`, and **refunds the claim** (`attempt = attempt - 1`): a released claim ended in no terminal state, so it is not an execution attempt; a deploy job still reaches exactly one terminal state and is never retried. Pausing writes a `job.paused` audit; a lock-wait requeue writes no audit (like the claim it undoes) and logs at INFO. `cancel_idle(db, job_id, actor, now)` cancels a `queued` or `paused` job with a `job.cancelled` audit; `InvalidJobState` is raised for any other status.
3. **Success hook and renewal advancement (§4.6, Plan 1 Extension points).** `mark_deployed` requires `job.status == succeeded`, which is only true after `finish()`. `JobRegistry.register(..., on_success=hook)` lets a handler run `hook(db, job, now)` inside the worker's `_finish` transaction right after `finish(..., 'succeeded')`, in a savepoint: the deploy hook resolves the renewal (`payload.renewal_id`, else the `issued` renewal whose `certificate_id` is the deployed certificate) and calls `mark_deployed(db, renewal_id, job.id, actor=<requester or system>, now)`. `InvalidTransition` (renewal cancelled meanwhile, no succeeded binding) is recorded as a `deploy.renewal_not_advanced` audit with the refusal reason and never fails the job; any other hook exception rolls back the savepoint only and is logged by class name. Paused, failed and cancelled deploys never advance a renewal, even when some hosts succeeded (Plan 1's `job_not_succeeded`).
4. **Advisory locks (§3.6).** `app/jobs/locks.py` opens dedicated connections from a `NullPool` engine sharing the application URL, so deploy concurrency (`deploy.concurrency` ≤ 50) cannot starve the regular pool. A deploy job holds one *job lock session* with `deploy:global` (exclusive) and `inventory:pull` (shared); each host run holds its own session with `deploy:<hostname>`. Keys are hashed with `hashtext(:key)` (`pg_try_advisory_lock`, `pg_try_advisory_lock_shared`), always `try`, never blocking. Closing the session releases every lock, which is also what happens when a worker dies. If `deploy:global` is taken the job raises `JobRequeued(now + 30 s)`; pausing closes every lock session. Web serializes deploy creation with `pg_advisory_xact_lock(hashtext('deploy:enqueue'))` (Contract decision 15).
5. **Inventory checkout (§6.1, §7.7, §3.6, §9.5, §9.7).** `refresh_checkout(remote, ref, checkout, *, env, now)` fetches `+<ref or HEAD>:refs/cert-dashboard/fetch` with `--no-tags`, then `git reset --hard refs/cert-dashboard/fetch` and `git clean -ffdx`, so a failed fetch never leaves a half-reset tree. A marker file `<inventory_root>/last_pull.json` (`rev`, `rev_date`, `pulled_at`) records the last successful pull; "older than 24 hours" means `now - pulled_at > 24 h`. Coordination: the job lock session tries `inventory:pull` **exclusively** to pull, then takes it **shared** and drops the exclusive hold; every Ansible run happens under the shared hold, so no reset can change files under a running playbook. If the exclusive lock is unavailable (another job is reading or pulling) or the last pull is younger than 60 s, the job uses the current checkout without pulling (`refreshed: false`), provided it is not older than 24 hours. A pull failure with a younger checkout proceeds with `warning: "pull failed; using the last good revision"`; with an older one it raises `JobFailure("transient_network", "inventory pull failed and the last good checkout is older than 24 hours")`. Git stderr is never stored. Discover and deploy results carry `inventory_rev` (40-hex commit SHA), `inventory_rev_date` (ISO 8601 UTC), `inventory_refreshed` and, when set, `inventory_warning` — the exact shapes Plan 2's digest and Overview read. `server.inventory_source = "<ref or HEAD>:<inventory.path or .>@<rev>"` (no URL). The worker does not re-validate `inventory.repo_url` (it is validated on every settings write) but restricts transports with `GIT_ALLOW_PROTOCOL=https:ssh:file`, which refuses `ext::` command transports.
6. **Secrets reaching git, SSH and Ansible (§3.4, §5.2, §6.1, §6.4).** `StagingArea(<key_staging_dir>, job_id)` creates `<dir>/<job_id>` `0700` (`O_NOFOLLOW`, refusing symlinks) and writes `0600` files with `O_CREAT|O_EXCL|O_NOFOLLOW`; it is removed in `finally` and by Plan 1's startup wipe. The SSH key (`Settings.ansible_ssh_key`) and, for deploys, the decrypted TLS key are staged there and passed **by path** only (`ANSIBLE_PRIVATE_KEY_FILE`, `key_pem_path`, `GIT_SSH_COMMAND -i <path>`). The vault password is passed as `CERT_DASHBOARD_VAULT_PASSWORD` in the child environment with `ANSIBLE_VAULT_PASSWORD_FILE` pointing at the executable `app/ansible/vault_client.py`, which prints that variable and exits non-zero when it is missing (fail closed, never an empty password). The Git token is passed as `CERT_DASHBOARD_GIT_TOKEN` with `GIT_ASKPASS=app/ansible/git_askpass.py` (username prompt → `x-access-token`, password prompt → the token), `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1` and an empty `credential.helper`, so nothing is stored in `.git/config`. `ansible-runner` runs with `suppress_env_files=True`; a canary test proves no artifact file contains the vault password, the Git token, vaulted plaintext or key bytes. Known hosts: `Settings.known_hosts_file` (environment `SSH_KNOWN_HOSTS`, default `/etc/ssh/ssh_known_hosts`, the path `docker-compose.credentials.yml` already mounts); a missing file fails discover/deploy jobs with `config_invalid` ("SSH known_hosts file is missing") before any connection.
7. **Runner environment, events and classification (§6.7, §9.4, §9.6).** `build_env` builds the child environment from scratch: `PATH` (the running interpreter's `bin` first), `HOME=<run_dir>/home`, `ANSIBLE_LOCAL_TEMP=<run_dir>/tmp`, `ANSIBLE_HOST_KEY_CHECKING=True`, `ANSIBLE_SSH_ARGS="-o StrictHostKeyChecking=yes -o UserKnownHostsFile=<known_hosts> -o IdentitiesOnly=yes -o BatchMode=yes -o ControlMaster=auto -o ControlPersist=60s"`, `ANSIBLE_PRIVATE_KEY_FILE`, `ANSIBLE_NOCOLOR=True`, `ANSIBLE_RETRY_FILES_ENABLED=False`, `ANSIBLE_PYTHON_INTERPRETER=auto_silent`, `ANSIBLE_DEPRECATION_WARNINGS=False`, `ANSIBLE_COLLECTIONS_PATH=<run_dir>/collections` (empty: only `ansible.builtin` is used) and the vault variables when configured; no proxy variables, nothing inherited — including the `ANSIBLE_SSH_ARGS` that `docker-compose.credentials.yml` sets on the worker, which this environment supersedes with a stricter equivalent (Task 20 documents that the compose value is no longer read). Playbooks publish structured per-host results through `ansible.builtin.set_stats` under `cert_dashboard.<inventory_hostname>` (global, aggregated), read from the `playbook_on_stats` event's `artifact_data`. `runner_on_unreachable` messages are classified **in memory only**: `Permission denied`, `Host key verification failed`, `REMOTE HOST IDENTIFICATION HAS CHANGED`, `No ED25519 host key is known`/`host key ... not known` → `auth` (stored message: "SSH authentication or host key verification failed; check known_hosts and the deploy key"), anything else → `transient_network` ("host unreachable over SSH"); the peer text is never stored. A run killed by its timeout is `host_timeout`. A run that fails without any host result (syntax error, missing module, unreadable key file) is a job-level `internal` failure "Ansible could not run the playbook; check the worker image" and marks no host failed (§9.6). `log_excerpt` = the last 200 stdout lines of that host's events, skipping every event whose result is censored by `no_log`, passed through `redact()`, at most 64 KiB.
8. **`discover.yml` shape (§6.2).** Two phases selected by the extra-var `discovery_phase`: `collect` (detect webserver and binaries via `tasks/detect_webserver.yml`, capture the dump) and `inspect` (stat/fingerprint the paths the worker parsed, passed as `paths_by_host`). The dump task is `no_log: true` and its output is written **to the controller** with `ansible.builtin.copy` `delegate_to: localhost`, `become: false`, mode `0600`, as `<artifact_dir>/dumps/<hostname>.txt` (≤ 16 MiB, else the host fails `dump_too_large`), so dumps never enter `job_events` or stdout and nothing is written on the target. Apache (§6.2 step 2): the dump is produced by the read-only collector `app/ansible/playbooks/files/apache_dump.py`, run with `ansible.builtin.script` (`python3`, A16; the only target-side `script` task of `discover.yml`, `become: true`, `no_log: true`, `timeout: 60`), and stored as `<artifact_dir>/dumps/<hostname>.json`. The collector runs `<apachectl> -S` (which is `-t -D DUMP_VHOSTS -D DUMP_RUN_CFG`: the spec's `DUMP_VHOSTS` output plus the `ServerRoot` line) and `<apachectl> -V` (`HTTPD_ROOT`, `SERVER_CONFIG_FILE`), each with a 25 s subprocess timeout, and builds the file list as the **union** of (a) every `(file:line)` file named by `-S` and (b) a recursive read of the main config: `Include`/`IncludeOptional` (case-insensitive, quoted or bare, relative to the current `ServerRoot` — the directive's value once seen, else `HTTPD_ROOT`), wildcards expanded in sorted order, a directory included means every file below it in sorted order, a missing `IncludeOptional` target is silent, a missing `Include` target or an unresolved `${VAR}` is a warning, cycles are cut by real path, depth ≤ 16, ≤ 500 files and ≤ 16 MiB in total (else the host fails `dump_too_large`). The spec's literal rule reads (b) only "when the file list cannot be derived"; the plan always performs it because `-S` lists only the files that define vhosts, so the file list of global-level directives (§6.2 Apache rule: `vhost_name = "default"`) and of included TLS snippets can never be derived from `-S` — skipping (b) would silently miss them. When `-S` fails or names no vhost, (b) is the only source and the warning `apachectl -S unavailable; vhosts derived from the configuration files` is recorded. Each file is emitted once, in walk order followed by the remaining `-S` files, after a `# configuration file <path>:` marker; the JSON document is `{"s_rc", "s_output", "server_root", "config_file", "files_from_s", "files_from_includes", "warnings", "config"}`. The collector only reads: it opens files with mode `"rb"`, imports only `argparse, glob, json, os, re, subprocess, sys`, and never creates, removes or changes a file (a unit test checks both its AST and a read-only directory tree; Ansible's own transient module copy under the SSH user's remote temp directory is the same as for every other module). Binary detection tries `command -v` and then `/usr/sbin`, `/usr/local/sbin`, `/usr/local/nginx/sbin`, `/usr/local/apache2/bin`; `apachectl` or `apache2ctl`. `inspect` returns per path: exists, readable, owner, group, octal mode, size, mtime, leaf fingerprint (`openssl x509 -noout -fingerprint -sha256`, normalized to lowercase hex without colons), RFC 2253 subject and issuer, and for keys `openssl pkey -in <path> -passin pass: -pubout -outform DER | openssl dgst -sha256` under `no_log: true`. `-outform DER` deviates from the spec's literal `openssl pkey -pubout | openssl dgst -sha256` deliberately: §4.5 defines key identity as the SHA-256 of the **DER** `SubjectPublicKeyInfo`, and hashing PEM text would never match `private_key.public_key_sha256`. A passphrase-protected key fails `-passin pass:` and yields `key_unreadable: true`. Every command task has `timeout: 60`; `become: true` only on the dump, stat, fingerprint and key-hash tasks. **Confirmed by operator decisions D2 and D3 (2026-10-25):** the DER `-outform DER` key hash above is D2 (the spec's PEM-text command is corrected), and the always-union Apache include read is D3 (the spec's "fall back when the file list cannot be derived" wording is corrected); no further review question remains on either point.
9. **Parser rules (§6.2, §10.1).** Both parsers return `ParsedBinding` candidates; `app/ansible/discovery.py` assembles final bindings after `inspect`. nginx: a tokenizer honouring quotes, escapes and comments; files attributed by `# configuration file <path>:` markers; only `http { server { … } }` blocks (a `stream` server is skipped with a warning); a block is TLS when any `listen` has `ssl` or the legacy `ssl on;` is present; ports from every TLS `listen` form (`443 ssl`, `[::]:443 ssl`, `127.0.0.1:443 ssl http2`, `*:443`), deduplicated, `unix:` skipped; `vhost_name` = first `server_name` that is not `_`/empty, else `default`; `vhost_names` = all names except `""`; `ssl_certificate`/`ssl_certificate_key` pair positionally (nginx requires equal counts); a server without its own `ssl_certificate` inherits the `http`-level one with `config_file` = the file of the inherited directive; relative paths resolve against `/etc/nginx`. Apache: vhosts from the `apachectl -S` lines (`port N namevhost NAME (file:line)`, `alias`, `default server`), directives from the matching `<VirtualHost>` block in the concatenated files; when `-S` produced no vhost line (`s_rc != 0` or empty), vhosts come from each `<VirtualHost addr:port>` section of the concatenation with its `ServerName`/`ServerAlias` (port from the address, else 443); TLS only with `SSLEngine on`, `SSLCertificateChainFile` → `chain_path`, a global-level certificate directive → `vhost_name = "default"` on the port of the first `Listen … https`/`Listen 443` (else 443), relative paths against `ServerRoot`. Extra certificate files (§6.2 "issuer-matching rule"): **superseded by operator decision D1 (2026-10-25).** The role of each certificate file is decided by verifying that file's own content, never by its position in the list and never by comparing DNs: every file is read and parsed on its own; a file with one certificate is a leaf candidate; a file with several certificates is a bundle whose first certificate is the leaf and whose later certificates are chain **only when each verifies the previous signature** (`issuer`/`subject` **and** signature verification via `app/crypto/chain.py`); a separate file is a chain only if it really signs that leaf. If verification is impossible (unreadable file, incomplete chain, missing issuer) the file is not used as a chain, stays a certificate of its own, and the binding carries the fixed incomplete-chain diagnostic. A same-CA RSA+ECDSA pair is therefore two bindings, never certificate + chain; the earlier positional reading ("a later certificate file whose subject equals the first file's issuer is the chain") is withdrawn, and the spec §6.2 prose is corrected in the same PR.
10. **Reconciliation (§6.3, §9.5).** `reconcile_host` upserts by the binding identity `(server_id, webserver, config_file, port, vhost_name, cert_path)` under the server row lock, updating paths, owners, modes (octal string → int), fingerprints, `certificate_id`, `match_state`, `last_seen_at = document.collected_at` and `notes`, and calls `audit_binding_state(db, binding, previous, actor, job_id=str(job_id), now=now)` for every insert (`previous=None`) and update — Plan 2's producer contract. States: fingerprint matches a certificate and the key hash equals that certificate's SPKI hash → `matched`; fingerprint matches but the key hash differs → `key_mismatch` with `certificate_id` set (the certificate is identified; the binding blocks deploys); no match → `unknown`, `certificate_id NULL`; certificate missing/unreadable, or key missing/unreadable/`key_unreadable` → `missing_file` with `certificate_id` kept from the previous state and the fixed note `"<file kind> missing or unreadable at discovery"`. A binding absent from the dump → `is_active=false`, note `removed from config at <UTC date>`. A host that previously had active bindings and now yields zero → nothing deactivated, `parse_suspected` recorded on the job host row and in the job result. A failed host keeps its bindings untouched; "stale" is derived for display (`server.last_discovery_status != 'ok'`), not stored. `server.last_discovery_at` and `last_discovery_status` (`ok|failed|unreachable`) are set on every attempt. Servers: inventory hosts without a row are inserted (`server.create` audit); active rows absent from the inventory become inactive with their bindings and derived endpoints (`server.deactivate` audit); `ansible_groups` (excluding `all`/`ungrouped`), `connection_address` (`ansible_host` when it differs from the hostname), `webserver` (inventory variable when valid, else the detected value) and `inventory_source` are refreshed on every discovery.
11. **Binding-derived endpoints (§4.9, A7, Plan 2 Extension points).** `ensure_binding_endpoint` in `app/services/endpoints.py` derives the endpoint of a binding's `vhost_name:port` (§4.9) as `host = server.connection_address or server.hostname` (the address the worker reaches), `port = binding.port`, `sni = verify_sni(vhost_name, vhost_names)` (first name that is a plain DNS name — no wildcard, not `default`/`_`, not an IP literal — else NULL; NULL when equal to the host), `source='discovery'`, `server_id`, `binding_id`. Identity is the existing unique index `(host, port, coalesce(sni, host))`, so bindings that resolve to the same identity (an RSA+ECDSA pair of one vhost, or two wildcard/default vhosts on one port) share one endpoint linked to the lowest active binding id; the others are recorded in the discover row's `precheck.shared_endpoints`, never inserted twice. An existing endpoint with that identity and `binding_id NULL` (a manual endpoint) is adopted — `server_id`/`binding_id` set, `source` kept `manual`; one linked to another binding is reused as is. Expectation: the binding's `certificate_id` when the binding is `matched` (set or updated on every discovery); an `unknown` binding has no inventory certificate, so its endpoint keeps a NULL expectation and reports `mismatch` per §4.10 until one is set — the only exception to A7, which cannot be met without importing the certificate. Deactivated bindings deactivate the derived endpoints they own (§4.9) unless another active binding shares it, in which case the link moves to that binding. Audits `endpoint.create`/`endpoint.update` with `source: "discovery"`.
12. **Discovery jobs (§6.2, §7.1, §7.2, §9.5).** Payloads: `{}` (whole inventory; schedule and "Discover all"), `{"hosts": [...]}` (1–500 unique inventory hostnames) or `{"groups": [...]}` (1–50 group names); names must match `[A-Za-z0-9_.-]{1,253}`, so `--limit` patterns are built only from validated names joined with `:` and can never carry Ansible pattern syntax. Priority 200 on demand, 100 scheduled (`register_schedule("discovery", JobType.DISCOVER)`, time `discovery.nightly_at`, flag `discovery.enabled`, `scheduled_reason='nightly'`). One `job_host` row per targeted server (`binding_id NULL`): `running` → `succeeded`/`failed` with `error_message` `"<reason>: <fixed text>"` (`unreachable`, `auth`, `dump_failed`, `dump_too_large`, `parse_failed`, `host_timeout`) and `precheck` = the raw dump summary (`webserver`, `binaries`, `config_files` (≤ 200), `bindings`, `warnings`, `parse_suspected`, `dump_bytes`, `dump_sha256`). Per §6.7 and Plan 2 Contract decision 1: if any host is unreachable and `attempt < max_attempts`, the handler commits every other host and raises retryable `transient_network`; the retry discovers only the hosts whose row in this job is still `unreachable`. The job succeeds when at least one host was discovered; when none was, it fails with `auth` if any host failed authentication, else `transient_network`. Raw facts: dumps and each host's §6.2 document (`<artifact_dir>/discovery/<hostname>.json`, `0600`) stay under `job.ansible_artifact_dir = <artifacts_root>/<job_id>`, pruned by Plan 1's 30-day artifact cleanup; the UI shows only the summary. `discovery.run` is audited once per attempt with counts. Result: `inventory_*` keys plus `hosts`, `ok`, `failed`, `unreachable`, `bindings_added`, `bindings_updated`, `bindings_deactivated`, `endpoints_created`, `servers_created`, `servers_deactivated`, `parse_suspected` (hostnames).
13. **Test pull is `discover/test_pull`.** The web process has no inventory volume or Git token, so Settings → Inventory "Test pull" enqueues `{"action": "test_pull"}` (priority 200, `max_attempts=1`). The handler runs the inventory preparation and `ansible-inventory --list` only (no SSH to targets) and returns `inventory_*` keys plus `hosts` and `groups` counts. Being a `discover` job it needs a worker with the SSH key; the Settings tab says so when no such worker is alive (Contract decision 22). Settings shows the newest test pull and the current revision (newest succeeded discover/deploy result), never a guessed state.
14. **Rollout planning (§6.5, §10.1).** Pure functions in `app/services/deploy.py`. A server's rotation group is its lexicographically smallest Ansible group (`ungrouped` when it has none). Default canary: count affected servers per group over all memberships, take the smallest group (ties by name) and its first server by hostname. Remaining servers: groups sorted by name, servers in each group sorted by hostname, taken round-robin. `batch_size = max(1, ceil(total_servers * batch_percent / 100))` with `total_servers` **including** the canary; batch 0 is the canary, the rest are consecutive chunks of `batch_size`, the last possibly smaller. The plan is deterministic (no randomness); the "seeded ordering" of §10.1 is this total order. **Batch execution (§6.5 "first failed host stops the rollout").** `run_batch(hosts, *, concurrency, run_one, failed, should_stop)` in the same module runs one batch on a `ThreadPoolExecutor(max_workers=concurrency)` with **incremental submission**: it submits hosts in plan order only while fewer than `concurrency` submitted futures are unfinished, waits with `concurrent.futures.wait(..., return_when=FIRST_COMPLETED)`, and after the first result for which `failed(result)` is true (or a `run_one` exception, which counts as a failure) — or once `should_stop()` returns true (operator cancel, Task 17) — submits nothing more; it then waits for every in-flight host and returns `BatchRun(results, not_started, stopped_by)`. It never calls `executor.map` or submits the whole batch up front, because a queued-but-unstarted future would still execute after the failure. Rows of hosts in `not_started` are never claimed (`pending`), so the handler's `skip_pending(..., "rollout_stopped", from_batch=<current batch>)` marks them and every later batch `skipped`. A `skipped`/`locked` host is not a failure.
15. **Targets, eligibility and one active deploy (§6.5, §8.7, §3.6, §3.9).** Default targets: active bindings of active servers whose `certificate_id` is the new certificate's `renews_id`, plus bindings already matched to the certificate itself (re-deploy). Explicit selection: any listed active binding of an active server, narrowed by the group/host filter. Excluded always: `key_mismatch`, `missing_file`, inactive bindings or servers. `unknown` bindings only with `include_unknown`, audited as `deploy.include_unknown` (binding ids). Guardrails (§8.7) refuse to start when the certificate has no key or its key version is missing from the keyring, is expired or not yet valid, is `revoked`, every target binding already has the new on-disk fingerprint ("already deployed everywhere"), there is no target, or a deploy job is `queued`, `running` or `paused` — `queued` is added to the spec's "running or paused" because a queued deploy is about to take `deploy:global`, and admitting a second one would only park it behind the first; the refusal names the job and links it. Creation runs under `pg_advisory_xact_lock(hashtext('deploy:enqueue'))`, so two operators cannot both pass the check. The preview carries `plan_sha256` (SHA-256 of the canonical JSON of certificate id, sorted binding ids, canary server id, batch percent, pause flag, include-unknown flag and chain status); the enqueue POST must echo it and confirm the sentence naming the host count and the canary hostname; a changed plan returns 422 with the new preview. The job (`priority=300`, `max_attempts=1`) and all `job_host` rows (`pending`, `batch_no`, `binding_id`, `old_fingerprint` = the binding's on-disk fingerprint — the "discovery snapshot in the job" — and `new_fingerprint` = the new certificate's fingerprint) are written in one transaction with `deploy.start` (certificate, host and binding counts, canary, batch sizes). Payload: `certificate_id`, `renewal_id` (or null), `batch_percent`, `pause_after_canary`, `include_unknown`, `chain_override` (bool), `chain_status_at_plan`, `plan_sha256`, optional `retry_of`. §6.5's "optional deploy window" is implemented as an optional *not before* time (UTC, at most 7 days ahead) stored as `job.run_after`; window ends and approval gates are §12 item 9 future work.
16. **Trust gate and guardrails (§5.8, §6.5, §8.4).** `assess_certificate(db, certificate_id, validation_time)` (new in `app/services/trust_anchors.py`, sharing the per-row body of `recheck_chain_statuses`) assesses one certificate and persists a changed status with the usual `certificate.chain_check` audit. It runs at preview, at enqueue and on every claim of the job (start and resume). Not `trusted` at enqueue → the operator must supply a reason (1–500 characters); the job records `chain_override: true` and `chain_status_at_plan`, and a `deploy.chain_override` audit is written with `certificate_id`, `previous_status`, `job_id` and `reason` in the same transaction. At execution: `trusted` → proceed; not trusted with an override whose `chain_status_at_plan` equals the current status → proceed; anything else (trust lost after a trusted plan, or a different non-trusted status) → `JobFailure("config_invalid", "certificate trust changed since the deploy was planned; plan it again")`. Independently and always: certificate `active`, `not_before <= now < not_after`, key present, unwrappable and matching the leaf's SPKI hash (`key_unwrap` / `config_invalid`), and per host the binding is still active and not `key_mismatch`/`missing_file` (`binding_blocked`), plus the on-target drift and config tests. Job-level gate failures mark every pending row `skipped` with `job_failed`.
17. **Host execution contract (§6.4, §4.8, Plan 1 Extension points).** `plan_file_writes(targets)` maps every distinct path to exactly one write: `cert_path` gets the leaf when the binding has a `chain_path` (which gets the chain), otherwise the full chain (leaf + chain, which nginx and Apache ≥ 2.4.8 both serve from `SSLCertificateFile`/`ssl_certificate`); `key_path` gets the key. Several bindings sharing a path produce one write listing all binding ids; the same path needed with different content (for example one binding's key path is another's certificate path) raises `FileConflict` and fails that host `file_conflict` before Ansible runs. Extra-vars: `job_id`, `cert_pem_path`, `chain_pem_path`, `fullchain_pem_path` (artifact dir, public), `key_pem_path` (staging tmpfs), `backup_retention_days`, `webserver`, `files` (path, source variable, kind) and `targets` (binding id, cert/chain/key paths, `expected_fingerprint` = `old_fingerprint`, `new_fingerprint`, port, SNI). Preflight drift: the on-disk leaf fingerprint must equal `expected_fingerprint` **or** `new_fingerprint` (the latter is §6.4 step 9's idempotent case, never drift); files whose current content already matches are not written, but config test, reload and verify still run. Owner/group come from the file's current `stat`; mode: key `0600`, certificate/chain `old_mode & 0o644` (so `0640` stays `0640`, `0664` becomes `0644`). Each write is three explicit steps, exactly §6.4 step 3: `ansible.builtin.file` creates `<dir>/.<name>.cert-dashboard.tmp` empty with the final owner, group and mode (so the mode is set before any content exists), `ansible.builtin.copy` fills that existing file (same `mode`/`owner`/`group`, `no_log: true` for keys), and `ansible.builtin.command: mv -f -- <tmp> <target>` renames it atomically on the same filesystem. Reload: `<nginx> -s reload` / `<apachectl> graceful`; config test: `<nginx> -t` / `<apachectl> configtest`; verify: `openssl s_client -connect 127.0.0.1:<port> [-servername <sni>] -showcerts` with SNI from `verify_sni` (Contract decision 11), comparing the leaf fingerprint and recording the chain length. `restorecon -F -- <paths>` only when `restorecon` exists. Free space via `df -Pk` per target directory. **Fail-safe write scope (§6.4 steps 3–8, §9.6).** The playbook sets `deploy_step=writing` immediately *before* the first live write, and the write, label, config-test, reload and verify tasks are all inside one `block` whose `rescue` includes `tasks/rollback.yml` whenever `deploy_step` reached `writing`: a failure in the middle of step 3 (one file replaced, the next not) or in step 4 has already changed served files, so the rollback covers steps 3–7, a superset of the spec's 5–7 that only adds protection. The rollback restores **every** path of the manifest from the backup (each distinct path once, with the same temp-file + `mv` method and the original owner/group/mode), not only the paths known to be written, so a partially completed write is always undone. No live-file write task exists outside that block (a static test in Task 15 enforces it), and no task introduces a write path without its rollback (Task 14's playbook stops after the backup). Backup pruning runs `files/prune_backups.py` with `ansible.builtin.script` (`python3`, A16) only after a successful host run; it removes `<job_id>` directories whose `manifest.json` `created_at` is older than the retention unless they hold the newest backup of some path; retention `0` prunes nothing.
18. **Host outcomes (§6.4, §9.6, §8.7).** `job_host.status`: `succeeded` (only with published `step == "verified"` evidence for every target binding — a run that ends without that evidence, however it ends, is never a success: with no write started it is `failed`/`internal` "deploy playbook ended before verification"); `rolled_back` (a step 3–7 failure whose rollback restored, reloaded and verified the old fingerprint; `rolled_back=true`, `error_message` = the original error) — §6.4 step 8 has the playbook "report `failed`" with the rollback outcome, and the worker stores that report as the §4 enum value `rolled_back` so the UI, digest and totals can tell a cleanly restored host from one needing attention; `failed` (preflight failure with no change, or a failed rollback with `rolled_back=false` and `rollback_error`); `skipped`. `error_message = "<reason>: <fixed text>"` with reasons `drift_detected`, `missing_target`, `permission_denied`, `insufficient_space`, `baseline_config_invalid`, `key_mismatch_preflight`, `backup_failed`, `write_failed`, `config_test_failed`, `reload_failed`, `verify_failed`, `unreachable`, `auth`, `host_timeout`, `binding_blocked`, `not_in_inventory`, `file_conflict`, `internal` (plus Plan 1's `worker_lost`); skipped rows carry `locked`, `rollout_stopped`, `cancelled`, `pause_expired`, `job_failed` or `job_ended` (no reason column exists; `error_message` holds it). A failed rollback and any `host_timeout` (a killed run publishes no result, so the worker cannot know whether writes started) both set `rollback_error`, write a `deploy.rollback_failed` audit and are shown as **needs manual attention**; a successful rollback writes `deploy.rollback`. A rollout stopped by a host fails the job with `JobFailure(<class>, "rollout stopped: <hostname> failed (<reason>)")`, class `transient_network` for `unreachable`, `auth` for `auth`, `timeout` for `host_timeout`, `internal` for `internal`, `config_invalid` otherwise; deploy policy never retries any of them.
19. **After a host succeeds (§6.4 step 7, §6.6, Plan 2 producer contract).** In the same transaction as the host's rows, each target binding gets the verified state — `on_disk_fingerprint = new`, `on_disk_key_public_sha256 = <new key SPKI hash>`, `certificate_id = new`, `match_state = matched` — through `audit_binding_state(..., job_id=<deploy job id>)`, and its derived endpoints expect the new certificate (`endpoint.update` audit). Without this the next deploy before a discovery would report false drift and every scan would report `mismatch` after a successful deploy. `last_seen_at` stays a discovery-only field. The worker-side informational check (§6.4 step 7, A17) calls Plan 2's `observe_endpoint(host, port, sni, scan.timeout_seconds)` for each derived endpoint and stores `{status, fingerprint, matches}` under `precheck.worker_verify`; it never influences the host outcome.
20. **Operator controls and sweeps (§6.5, §7.1, §8.7).** Continue (`paused` only, before expiry): `queued`, `run_after = now`, `scheduled_reason='manual'`, `paused_at = NULL`, `deploy.continue` audit; the next claim re-acquires locks, re-pulls the inventory, re-runs the trust gate and every host's drift preflight. Cancel: `queued`/`paused` → `cancel_idle` with every pending row `skipped` (`cancelled`); `running` → pending rows `skipped` (`cancelled`) under row locks, the handler lets in-flight hosts finish or roll back, then raises `JobCancelled`. Both audit `deploy.cancel`. The handler claims a host's rows with `UPDATE … SET status='running' WHERE status='pending'`, so a cancelled row is never started. Sweep tick step `deploy_sweep` (`register_tick_step(..., requires=(JobType.DEPLOY, "default"))`): paused jobs with `paused_at < now - deploy.pause_timeout_hours` → `cancel_idle`, rows `skipped` (`pause_expired`), `deploy.pause_expired` audit; terminal deploy jobs that still have `pending` rows (left by the reaper, which only fails `running` rows) → `skipped` (`job_ended`). Retry host: allowed for a `failed`/`rolled_back`/`skipped` server of a terminal job, creates a **new** job for that server's binding ids (canary only, no pause) through the same guardrails and trust gate, with a required reason audited as `deploy.retry_host` (`from_job`, `server_id`, `reason`) besides `deploy.start`.
21. **Deploy timeout (§7.2, Plan 1 Task 13).** `deploy_timeout_seconds(db, job) = distinct server_id of pending rows with batch_no >= job.resume_from_batch × deploy.host_timeout_seconds + 900`, registered with `register_timeout(JobType.DEPLOY, ...)` in `worker.py`; `release_claim` clears `timeout_at`, so a paused or requeued job is never reaped.
22. **Worker capability signal (§9.2).** The web process cannot see worker secrets, and `worker_heartbeat` has no capability column, so `run_worker` writes one `worker.start` audit row at startup (`worker_id`, `ssh_key_present`, `known_hosts_present`, `vault_password_present`, `inventory_token_present`; booleans only). `worker_capabilities(db, now)` returns the newest such row whose worker has a fresh heartbeat. Missing SSH key → blocking banner "Discovery and deploy are unavailable: the worker has no ansible_ssh_key" on Servers, Deploy and Settings, and their buttons are disabled with that reason; an empty `inventory.repo_url` disables discovery and test pull with "No inventory repository is configured".
23. **§10.2 scenario 9 arithmetic.** With 3 servers at 50%, §6.5's formula gives batches `[1, 2]` — there is no third batch to skip. The plan keeps the formula normative and runs the scenario at 33% (`[1, 1, 1]`: the second batch fails, the third is `skipped`), plus a 50% variant proving that an in-flight host of the failing batch still finishes.
24. **§10.4 acceptance.** Real hosts stay out of the test suite. Task 20 automates every §10.4 item against the container targets (with the fixture CA standing in for the CA portal and a staging database in the same Postgres container) and adds a runbook to `docs/operations.md` listing the same checklist for the first production use against real hosts, with the evidence to record. Neither replaces the other; the plan does not claim the production run happened.

def test_first_failure_stops_submission_and_lets_the_in_flight_host_finish():
    h1_failed, h2_started = threading.Event(), threading.Event()
    started, active, peak, lock = [], [0], [0], threading.Lock()
    def run_one(host):
        with lock:
            started.append(host); active[0] += 1; peak[0] = max(peak[0], active[0])
        try:
            if host == "h1":
                assert h2_started.wait(5)             # fails while h2 is certainly in flight
                return "failed"
            if host == "h2":
                h2_started.set()
                assert h1_failed.wait(5)              # slow host: still running when h1's failure is seen
                time.sleep(0.2)
            return "succeeded"
        finally:
            with lock:
                active[0] -= 1
    def failed(result):
        if result == "failed":
            h1_failed.set()
        return result == "failed"
    run = run_batch(["h1", "h2", "h3", "h4", "h5"], concurrency=2, run_one=run_one, failed=failed)
    assert sorted(started) == ["h1", "h2"]            # h3-h5 were never submitted, so never started
    assert run.results == {"h1": "failed", "h2": "succeeded"} and run.stopped_by == "h1"
    assert run.not_started == ("h3", "h4", "h5") and peak[0] <= 2

## Extension points and open questions

- **Schema:** still frozen; Plan 3 adds no migration, column, enum value, index or settings row. Things a future migration could make cleaner, all worked around here: a `job_host.skip_reason` column (reasons live in `error_message`, Contract decision 18); a worker capability column on `worker_heartbeat` (signalled through the `worker.start` audit, Contract decision 22); a discovery-summary column (the raw dump summary lives in the discover row's `precheck`, Contract decision 12); a `job.attempt` that counts claims separately from executions (released claims are refunded, Contract decision 2).
- **Open questions for review (non-blocking):**
  - **Superseded by operator decision D1 (2026-10-25).** The chain rule is not "a later certificate file whose subject equals the first file's issuer is the chain". Every certificate file is parsed on its own; a bundle's later certificates are chain only when each verifies the previous signature (`issuer`/`subject` **and** signature verification, `app/crypto/chain.py`), and a separate file is a chain only if it really signs that leaf. Otherwise the file stays a certificate of its own and the binding carries the fixed incomplete-chain diagnostic. A same-CA RSA+ECDSA pair is two bindings, not certificate + chain.
  - **Superseded by operator decision D2 (2026-10-25).** The key hash is the SHA-256 of the DER `SubjectPublicKeyInfo`, not of PEM text: `openssl x509 -in <cert> -pubkey -noout | openssl pkey -pubin -outform DER | sha256sum` and `openssl pkey -in <key> -pubout -outform DER | sha256sum`, compared as lowercase hex with `private_key.public_key_sha256`. The round trip PEM-imported = PFX-imported = host command is covered by the D2 tests; the spec prose is corrected accordingly.
  - **Superseded by operator decision D3 (2026-10-25).** Apache discovery always unions the `apachectl -S` file list with a recursive read of the main config's `Include`/`IncludeOptional` paths, because `-S` names only files that define vhosts; the spec's "fall back when the file list cannot be derived" wording is corrected. For nginx, `nginx -T` provides the content of every `include`d file after its own `# configuration file <path>:` marker, and `app/ansible/parse_nginx.py` resolves each `include` reference against those already-dumped marker sections — relative paths against the `/etc/nginx` prefix, globs sorted, cycles cut, depth and expansion-count bounded — and splices the included content into the enclosing scope, so a directive from an included file belongs to the block that included it exactly like an inline one; a non-glob reference that is absent from the dump is skipped with a warning, and no additional file is ever read on the target.
  - Automatic rollback covers failures from the first live write through verification (steps 3–7), a fail-safe superset of §6.4 step 8's "steps 5–7", because a failure in the middle of step 3 or in step 4 has already replaced served files; the rollback restores every manifest path (Contract decision 17).
  - §10.2 scenario 9 cannot produce a third batch with 3 servers at 50% under §6.5's formula; the scenario runs at 33% (Contract decision 23).
  - The Git token username is fixed to `x-access-token` (GitHub/Gitea convention; GitLab personal and project access tokens accept any username). GitLab *deploy tokens* need their own username, which would require a new setting or secret format (Contract decision 6).
  - The deploy guardrail also refuses while a deploy is `queued`, and §6.5's "deploy window" is a *not before* time only (Contract decision 15).
  - Discovery parser fixtures are format-exact hand-written dumps plus the live dumps of the container targets; real anonymized production dumps (§10.1) should be added after the first §10.4 run on real hosts.
  - Raw configuration dumps can contain inline credentials of the target's own configuration; they are kept only on the worker's artifacts volume (`0600`, 30-day cleanup) and never shown in the UI (Contract decision 12).
- **Future work hooks (§12):** job-level rollback and approval gates/windows can be built on the paused-job contract (`release_claim`, `resume_from_batch`); more target types need a per-target deploy driver behind `run_host_deploy` and new parsers beside `parse_nginx`/`parse_apache`; network discovery can feed `reconcile_host` with documents of the same §6.2 shape.
